Vérification des sources · 13 novembre 2026

Peut-on vraiment piloter Kaggle et Colab à distance, avec une clé ?

Vous avez demandé de vérifier. Je suis allé chercher les documentations officielles et je cite les phrases exactes. Une de mes affirmations précédentes était trop absolue : je la corrige plus bas.

OUI — vérifié pour Kaggle.

Kaggle est officiellement conçu pour ça. La documentation ne dit pas seulement que c'est possible : elle classe explicitement l'usage par jeton API dans un environnement CI/CD comme un cas d'usage prévu. Une commande suffit à faire créer et exécuter une machine distante, sans navigateur.

1Kaggle : les 3 preuves officielles

Trois extraits, tirés de la documentation Kaggle elle-même. Aucune interprétation.

Preuve 1 — la commande crée le kernel et l'exécute

"This command uploads your local kernel file and its metadata to a Kaggle. If the kernel specified in the metadata exists under your account, it will be updated. Otherwise, a new kernel will be created. After uploading, Kaggle will attempt to run the kernel."

Source : documentation officielle du Kaggle CLI → github.com/Kaggle/kaggle-cli/blob/main/docs/kernels.md (section kaggle kernels push)

Preuve 2 — les jetons sont prévus pour l'automatisation

"API Keys & Personal Tokens: For automated scripts, notebook workflows, CI/CD environments, and direct SDK calls, create an API token from your Kaggle account API tokens settings page."

Source : documentation officielle de l'API Kaggle → kaggle.com/docs/api (section Authentication)

Preuve 3 — Kaggle a même un serveur MCP distant officiel

"The remote server URL is https://www.kaggle.com/mcp"
Authentification : OAuth 2.0 ou jeton Bearer (préfixe KGAT)
Outils exposés : create_notebook_session, get_notebook_session_status, cancel_notebook_session, download_notebook_output…

Source : documentation officielle → kaggle.com/docs/mcp

Concrètement : un agent (ou votre script) muni d'un jeton peut créer une session de notebook, suivre son état, récupérer sa sortie et l'annuler — entièrement par API. C'est exactement le mécanisme que notre chaîne utilise.

2Colab : ma correction

Ce que j'avais dit, et qui était trop absolu J'ai écrit : « Colab n'a pas d'API d'exécution publique ». C'est vrai pour le lancement headless officiel, mais incomplet : un serveur MCP communautaire, configuré avec OAuth, exécute bien du code dans un runtime Colab sans onglet de navigateur.

Ce que dit le dépôt officiel de Google (colab-mcp)

"An MCP server for bridging your local agent to a Colab session in the browser."

"This MCP server requires client support for notifications/tools/list_changed and for the client to be running locally on your device."

Source : github.com/googlecolab/colab-mcp (README officiel)

Ce que fait un fork communautaire (non officiel)

"With OAuth configured it connects directly to the Colab Jupyter runtime, so code execution and output streaming do not require a browser tab."

"change_runtime tool (GPU control) — Removed in official, working via OAuth in this fork."

Source : github.com/ats05/colab-mcp et le fork SebastianGilPinzon/colab-mcp — projets communautaires, non maintenus par Google

Pourquoi Colab reste un repli, pas le pivot
  • Non officiel : le pilotage sans navigateur passe par du code communautaire, qui peut casser à chaque mise à jour de Colab.
  • Le runtime meurt quand même : coupure à l'inactivité (~90 min constatés par les utilisateurs) et plafond de 12 h. Le pilotage à distance ne change pas la durée de vie de la machine.
  • Risque de conditions d'utilisation : Colab réserve son offre gratuite à un usage interactif et documente des restrictions sur l'automatisation non interactive ; Kaggle, lui, documente l'usage CI/CD. C'est la différence décisive.

4« Les clés » — ce que c'est vraiment, et le risque

Le mot « clé » recouvre deux choses très différentes. La distinction est essentielle pour votre sécurité.

TypeCe que ça permetÀ faire / ne jamais faire
Mot de passe Tout. Y compris changer le mot de passe, fermer le compte, accéder aux moyens de paiement. Ne jamais donner, à personne, à aucun agent.
Jeton API
(ce dont on parle)		 Uniquement les actions prévues par la plateforme : lancer un kernel, lire un statut, télécharger une sortie. Révoquable en 1 clic, sans changer votre mot de passe.
Le modèle de sécurité de notre chaîne, en 4 règles
  • Le jeton ne vit que dans les « secrets » de GitHub, chiffrés, jamais dans le code, jamais dans un fichier versionné, jamais dans un kernel.
  • Un jeton par usage : si quelque chose fuit, on révoque un seul jeton, pas tout.
  • Révocation immédiate : un clic sur Kaggle → Settings → API → révoquer. La chaîne s'arrête net.
  • Je ne dois jamais détenir vos jetons. Ni moi, ni aucun agent dans cette conversation. Vous les déposez dans GitHub, et le système les lit à l'exécution.
Le vrai danger n'est pas le pilotage, c'est la clé exposée Un jeton publié dans un dépôt public est scrapé en quelques minutes. C'est pourquoi le dépôt contient un test automatique qui échoue si un fichier ressemblant à une clé ou un jeu de données est versionné (test_kernel_script_contains_no_secret_and_no_formula + contrôle en CI).

Conclusion Votre intuition était juste : oui, un système peut piloter une plateforme de calcul à distance avec un jeton, de façon automatisée, sans vous. Ce n'est pas un contournement : c'est un usage prévu et documenté par Kaggle. La seule chose qui reste hors d'atteinte, et qui doit le rester, ce sont vos décisions scientifiques — pas les machines.
Ce que je ne peux toujours pas affirmer Je n'ai pas exécuté cette chaîne avec un vrai jeton Kaggle (je n'en ai pas, et je ne dois pas en avoir). La documentation prouve que le mécanisme existe ; elle ne prouve pas que votre compte, dans votre région, obtiendra la machine immédiatement. La preuve finale est le test de 10 minutes décrit dans le document « Qui lance quoi », section 4.
