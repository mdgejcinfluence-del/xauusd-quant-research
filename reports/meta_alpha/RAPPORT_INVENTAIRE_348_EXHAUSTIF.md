## 7. Conséquences sur DuckDB et le code V1 (analyse, aucune correction appliquée)

- **Lecture partition par partition** (le mode réel de `extract.py`, `segment.py`, `contracts_engine.py` : `read_parquet('<un fichier>')` avec sélection explicite de colonnes par nom) : **aucun impact**. DuckDB résout les colonnes par nom dans un fichier unique, et aucune variable certifiée n'utilise `bid_volume`/`ask_volume`.
- **Lecture multi-fichiers par glob** (`read_parquet('part_*.parquet')`) : DuckDB aligne par défaut **par position** — avec l'ordre différent du groupe 2, cela mélangerait silencieusement les colonnes (ex. `mid` recevrait `bid_volume`). L'option `union_by_name=true` corrige l'alignement ; la promotion `uint32`→`double` est alors exacte pour les valeurs entières ≤ 2^53, sans perte. **Le code V1 n'utilise aucun glob multi-fichiers à ce jour**, mais tout futur code devra imposer `union_by_name=true` — c'est une condition, pas une correction appliquée.
- **`bid_volume`/`ask_volume`** : quel que soit leur type, le projet les classe `UNAVAILABLE` comme volume réel (un tick n'est pas une transaction). Le changement `double`→`uint32` n'affecte donc aucun calcul scientifique autorisé ; il interdirait seulement toute lecture positionnelle naïve.
- **Types des colonnes utilisées** (bid, ask, mid, spread, timestamps, identifiants) : strictement identiques dans les 348 partitions. Aucun cast n'est nécessaire pour le pipeline certifié ; aucun n'a été appliqué.

## 8. Corrections nécessaires — propositions uniquement (non appliquées)

1. **Aucune correction du corpus** : ne pas réécrire/normaliser les Parquet (interdit, et inutile).
2. **Endurcir les futurs lecteurs** : imposer `union_by_name=true` dans tout futur `read_parquet` multi-fichiers, et ajouter un test qui échoue si une troisième signature apparaît.
3. **Conserver les deux signatures au registre** comme signatures acceptées, avec la frontière 294/295 documentée (déjà le cas dans `QUOTE_DGP_SPEC_V1.md`).
4. Optionnel (opération distincte à autoriser) : hachage SHA-256 complet des 348 fichiers en flux pour créer une baseline par fichier.

## 9. VERDICT : COMPATIBLE SOUS CONDITIONS

L'hétérogénéité est **technique, bornée et sans perte** : deux signatures nettes, mêmes 16 colonnes, types identiques pour toutes les colonnes scientifiquement utilisées, somme des lignes exactement égale au certificat (écart 0), continuité temporelle inter-partitions vérifiée par footers. **Conditions** : (a) lecture par nom de colonne (déjà le cas dans le code V1) ; (b) `union_by_name=true` obligatoire pour tout futur glob multi-fichiers ; (c) volumes jamais interprétés comme volume réel.
